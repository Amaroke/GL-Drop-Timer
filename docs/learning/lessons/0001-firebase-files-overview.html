1. What is Firebase?

Firebase is Google's backend-as-a-service platform: a set of managed products (database, authentication, file storage, hosting, functions...) that you call directly from your app, instead of writing and running your own server. Google operates the infrastructure; you write client code against their SDKs. (Firebase docs — Fundamentals)

GL-Drop-Timer uses two of those products:

ProductWhat it replacesUsed for
Firebase AuthenticationA login system and session management you'd otherwise build by handGoogle sign-in, knowing who's using the app
Cloud FirestoreA database server plus an API layer in front of itStoring and syncing each player's drop timers

Diagram — the browser talks straight to Google's servers. There is no GL-Drop-Timer server in between.

Compare that to a traditional setup: browser → your API server → your database. Firebase collapses the middle tier. The trade-off is that the rules living in firestore.rules (covered below) now do the job your API server's authorization code would normally do.

2. The console: projects and apps

Everything is managed at console.firebase.google.com. Two nested concepts matter:

  • Project: the top-level container. GL-Drop-Timer's project id is demo-gl-drop-timer (see .firebaserc, below). A project holds all the data, users, and settings.
  • App: a registration inside a project, one per platform (web, iOS, Android). GL-Drop-Timer registers one web app. Registering it is what generates the config object read in src/config/firebaseConfig.ts.

Source: Understand Firebase projects

Diagram, not a real screenshot — simplified layout of the console sidebar for a project on Spark.

Two things worth knowing before you touch the console yourself:

  • The Authentication → Sign-in method tab is where a provider (Google) gets switched on or off. Nothing in this repo can flip that toggle; it's a manual console step done once per project.
  • The Firestore Database → Data tab shows the live collection tree, exactly the shape drawn in section 4. It's the fastest way to check what a specific player's document actually contains.

3. Firebase Authentication, in depth

Firebase Auth is a hosted identity service: it verifies who a user is and hands your app a signed token, without you ever touching a password. GL-Drop-Timer wires up exactly one provider, Google, through signInWithPopup.

Diagram — the full round trip of a Google sign-in, matching src/auth/firebaseAuth.ts.

The four states the app tracks (restoring, signed-out, signing-in, signed-in) exist because step 4 isn't instant, and because the app needs to know on page load whether a previous session is still valid before it can show anything. restoring is that "don't know yet" window.

The Google account itself never touches GL-Drop-Timer's code. The popup, the password check, the 2FA if any, all of that happens on Google's own page. The app only ever receives the result: a uid, a display name, an email.

4. Cloud Firestore, in depth

Firestore is a document database: data lives in JSON-like documents, grouped into collections, which can nest subcollections inside a document. There's no fixed schema enforced by the database itself, only whatever the app and the security rules agree on. (Manage Cloud Firestore with the console)

users                        (collection)
└── {uid}                    (document, one per signed-in player)
    └── drops                (subcollection)
        └── {dropId}         (document, one per timer)
              readyAt: number | null
              updatedAt: number

Every path in the code (doc(db, "users", uid, "drops", key)) is just walking down this tree.

Two behaviors make this feel instant instead of like a network call every time:

  • onSnapshot: instead of asking once, the app opens a live listener on a document. Any change, made locally or by Firestore syncing from elsewhere, re-fires the callback automatically.
  • persistentLocalCache: Firestore keeps a copy of the data in the browser's IndexedDB. Reads come from that cache instantly, writes apply to the cache immediately too (optimistic), then get pushed to the server in the background. This is what lets GL-Drop-Timer work offline. (Access data offline)

5. Security rules: how a request gets judged

Because the browser talks to Firestore directly, something has to stand in for the authorization logic a normal API server would run. That's firestore.rules: code that Firestore's servers evaluate on every single read or write, before deciding to allow it.

Diagram — every read and write passes through this check, server-side, before it touches data.

function isOwner(userId) {
  return request.auth != null && request.auth.uid == userId;
}

match /users/{userId}/drops/{dropId} {
  allow read: if isOwner(userId);
  allow create, update: if isOwner(userId) && isValidDrop();
  allow delete: if isOwner(userId);
}

request.auth is the identity Firestore already verified through Firebase Auth; request.resource.data is the payload the client is trying to write. isValidDrop() additionally rejects any write that isn't shaped like { readyAt, updatedAt } with plausible timestamps, so even a signed-in owner can't write garbage into their own documents.

Source: Get started with Cloud Firestore Security Rules

6. The local emulator

Running against the real Firestore while developing means every test write is real, and mistakes are hard to undo. The Local Emulator Suite runs a fake Firestore on your machine that behaves like the real one, including enforcing the same firestore.rules, but resets whenever you want.

firebase emulators:start

GL-Drop-Timer configures it to listen on port 8080 (see firebase.json below), which is also what firestoreRules.emulator.test.ts and the other *.emulator.test.ts files in src/store/ connect to. That's how the test suite can assert "this write should be denied" without touching production data.

Source: Install, configure and integrate Local Emulator Suite

firestore.rulesFirestore

Covered in full in section 5: it's the server-side gate that lets a user only touch users/{their own uid}/drops/*, and only write documents shaped like { readyAt, updatedAt }.

firestore.indexes.jsonFirestore

{ "indexes": [], "fieldOverrides": [] }

Empty for now: no query in the project needs a composite index. Firestore auto-creates a single-field index for every field; this file only matters for more complex queries (sorting on multiple fields, combined filters). The day a query fails with an error that hands you an index-creation link, the entry lands here.

src/config/firebaseConfig.tsConfig

export function readFirebaseConfig(): FirebaseOptions {
  return {
    apiKey: import.meta.env.VITE_FIREBASE_API_KEY,
    authDomain: import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
    projectId: import.meta.env.VITE_FIREBASE_PROJECT_ID,
    appId: import.meta.env.VITE_FIREBASE_APP_ID,
  };
}

Builds the FirebaseOptions object from Vite environment variables (prefixed VITE_ so they get exposed to the browser, see .env.example). This apiKey is not a secret: it identifies the Firebase project, not a user. The real protection is firestore.rules.

8. The full lifecycle, start to finish

Sign-in → signInWithPopup returns a uid → that uid builds the path users/{uid}/drops/{dropId} → every read/write on that path goes through firestore.rules, which checks request.auth.uid == uid. No sign-in, no uid, no access: the whole security model hangs on that one thread. Free plan (Spark) covers all of it: Auth and Firestore both have a generous free quota, no card required.
